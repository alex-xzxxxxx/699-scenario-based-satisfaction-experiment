Two things worth recording about how V0 met the harder constraints:

- **§1 storage.** `db.js` reads `data/db.json` from disk on every call and
  writes it back through a temp file and rename. This is the constraint added
  in v1.1 after the Q1 review — without it, `npm run reset` would be a no-op
  against a running server and every test after the first would have run on
  contaminated state, silently, while still passing.
- **R27.** Each account record carries a random `token`. A session naming an
  account from an earlier state of the data cannot be mistaken for a later
  account that reuses the same numeric id. R27 has no test in suite B because
  no route deletes a user; V0 implemented it anyway.

### A finding for EQ4, recorded now rather than in Week 10

**Suite A is not thin.** The proposal cites Liu et al. (2023) as grounds to
expect an AI-written suite to be shallow, and EQ4 is built on comparing what
such a suite misses against what scenarios catch. This suite is 230 cases and
names every one of the thirty requirements, including the subtle ones — R25
indistinguishability, R28 cache headers, R30 deterministic ordering.

Suite B is planned at about 25 cases. The comparison is therefore 230 against
25, which is not the asymmetry the premise anticipated.

This does not invalidate EQ4. Case count is not coverage, and a suite written
by the same model that wrote the application may share its blind spots — which
is precisely what an independent suite and the scenario library are for. But
the claim EQ4 can support has changed shape, and the final report should say
so rather than restating the premise as though it held.

### The first run, and what it actually found

The first run was 14 passed, 11 failed. Every one of the eleven was a fault in
suite B, not in V0. Triaged:

| Failures | Cause |
|---|---|
| 8 | Asserted a redirect to `/tasks` after create and edit. V0 goes to `/tasks/:id`. |
| 1 | Asserted an empty `<ul data-testid="task-list">` was visible. An empty list has zero height. |
| 1 | Searched the raw HTML for another user's task title. The string was the echoed search box value; zero task rows matched. |
| 1 | Searched the response body for a rejected over-length title. It was the form redisplaying the submitted input. |

Each was corrected by asserting the requirement instead of an implementation
detail — navigating explicitly rather than asserting an unmandated redirect,
counting task rows rather than scanning HTML, checking that no task was created
rather than that a string is absent. Those are the assertions a specification-only
author should have written in the first place, so the corrections did not make
suite B dependent on V0.

### Two gaps in v1.1, both surfaced by suite B

1. **§4 never says where a successful create or edit lands.** `/tasks` and
   `/tasks/:id` are both defensible. Sixteen ambiguities were closed in v1.1
   and this one survived.
2. **§3 says the message container is "always present, empty when there is
   nothing to show", while R12 requires a confirmation "shown once".** The two
   together mean the container persists after the flash clears, so a test for
   "shown once" must assert invisibility, not absence. Not contradictory, but
   underdetermined on first reading.

Neither was amended: `REQUIREMENTS.md` is frozen and V0 is built from it. Both
are reported.

**Suite A found neither**, and structurally could not: it was written by the
model that chose the redirect and wrote the container. This is the clearest
EQ4-relevant result of the week — suite B's value here was not finding defects
but finding places where the specification was underdetermined.
