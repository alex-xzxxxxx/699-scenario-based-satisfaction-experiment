# Repository guide

What each folder is for, how the pieces connect, and how to check every number
this project quotes. Written for someone picking the repo up cold — including
you, in Week 11.

---

## 1. What the experiment does, in one paragraph

A model writes a web application (**V0**) from a frozen specification. Three
copies are made with defects planted by hand at known severities (**V1, V2,
V3**). A library of **47 scenarios** describes what the application should do,
in prose rather than as assertions. Every scenario is executed against every
version, producing **188 evidence bundles**. Each bundle is then judged twice —
once by a language model, once by you, blind to which version produced it — and
the two sets of verdicts are compared. Two conventional test suites run
alongside as a baseline. The research question is whether the model's judgment
can stand in for yours.

Everything in the repository is one of: the thing under test, the thing that
describes it, the thing that runs it, the thing that judges it, or the record
of a decision.

## 2. The folders

| Path | What it holds | Why it exists |
|---|---|---|
| `app/` | the application under test | V0, generated from `app/REQUIREMENTS.md`. The defect branches change only `app/server.js` |
| `app/REQUIREMENTS.md` | 30 numbered requirements, R1–R30 | the single source of what "correct" means. Frozen at tag `req-v1.1` |
| `app/tests_a/` | test suite A | written with the spec in hand — the conventional baseline |
| `app/tests_b/` | test suite B | written independently, by you. EQ4's independence claim rests on this |
| `scenarios/` | the scenario library and its provenance | the instrument. Frozen at tag `scenarios-v1` |
| `scenarios/library/` | **47 YAML files, one per scenario** | what gets executed and judged |
| `harness/` | the code that runs and judges | execution, evidence collection, judging, comparison |
| `defects/` | the seeded-defect design and registry | ground truth: what is wrong in V1–V3, and where |
| `analysis/` | the scoring definition | how a version's four numbers are computed |
| `evidence/` | evidence bundles, one directory per run | **not committed** — regenerated by running |
| `data/` | the run manifest and verdict files | **not committed** — holds the run-id → version map |
| `logs/` | decision log and prompt log | why every choice was made, and every prompt sent to a model |
| `records/` | one folder per week, W01… | the weekly submissions |
| `report/` | the final report | empty until Week 10 |

**Why `evidence/` and `data/` are gitignored.** `data/run_manifest.jsonl` is the
only place the run-id → version mapping exists. If it sat in the repository
next to the bundles, the blinding would be decoration. It was committed once by
accident on 17 November and removed the same day.

## 3. How the pieces connect

```
app/REQUIREMENTS.md  ──(a model, in an isolated session)──>  app/  = V0
        │                                                      │
        │                                            defects/apply.py
        │                                                      ▼
        └──(you, and a model)──> scenarios/library/      defect/v1,v2,v3
                                         │                     │
                                         └──────┬──────────────┘
                                                ▼
                               harness/runner/runner.py   ← executes, never judges
                                                ▼
                                   evidence/<run_id>/     ← trace.json, trace.md,
                                                │           console.log, network.jsonl
                              ┌─────────────────┼─────────────────┐
                              ▼                 ▼                 ▼
                   harness/judge.py      you, reading        app/tests_a/
                   (+ logs/prompts/       trace.md           app/tests_b/
                    P-003.txt)                │              (run separately)
                              │               │
                              ▼               ▼
                   data/verdicts.jsonl   data/human-verdicts.jsonl
                              └───────┬───────┘
                                      ▼
                           harness/compare.py   ← reveals the version last,
                                                  from data/run_manifest.jsonl
```

The one rule that shapes all of it: **the runner executes and records; it never
decides whether a scenario passed.** If it did, there would be nothing left for
the two judges to disagree about, and the central measurement would have no
data.

## 4. Scenario ids

A scenario id is `<AREA>-<NN>`. The area is the part of the application it
exercises, and it matches the `use_case` field in the file.

| Prefix | Area | `use_case` | In the library |
|---|---|---|---|
| `REG` | registration | UC1 | 8 |
| `SES` | sessions — sign in, sign out, session lifetime | UC2 | 9 |
| `TSK` | tasks — create, edit, complete, delete | UC3 | 14 |
| `LST` | listing and search | UC4 | 7 |
| `ACC` | access control — one user reaching another's data | UC5 | 7 |
| `INT` | integration, spanning more than one area | cross | 2 |

So `SES-05` is the fifth sessions scenario and `TSK-17` the seventeenth task
scenario. The numbers are not contiguous: 74 candidates were drafted and 27
rejected, and the accepted ones kept their original numbers rather than being
renumbered, so the rejections stay traceable.

`use-cases.md` was later refined from these five areas into fifteen use cases
(D-016). The `use_case` field still names the **area**, because editing 47
frozen files for a label nothing reads would change the holdout set after it
was tagged. The finer placement is the table at the end of `use-cases.md`.

## 5. Every number this project quotes, and how to check it

Run these from the repository root.

| Claim | Command |
|---|---|
| 30 requirements | `grep -cE '^\| R[0-9]+ \|' app/REQUIREMENTS.md` — they are table rows, so the pipe needs escaping or `grep -E` reads it as alternation and matches almost every line |
| 47 scenarios, all valid | `python -m harness.runner.runner --check` |
| 74 candidates → 47 accepted | `python -c "import csv;r=list(csv.DictReader(open('scenarios/validation.csv')));print(len(r),sum(1 for x in r if x['decision']=='accepted'))"` |
| **suite A: 230 cases** | `pytest app/tests_a --collect-only -q \| tail -1` |
| suite B: 25 tests | `pytest app/tests_b --collect-only -q \| tail -1` |
| 14 seeded defects | the tables in `defects/registry.md` |
| which tags exist | `git ls-remote --tags origin` |

**On suite A's 230.** There are 83 `def test_` functions across six files;
pytest expands the parametrised ones to **230 cases** at run time. Both numbers
are true and they count different things — `--collect-only` is what settles it.
Suite B's 25 are 25 functions with no parametrisation. The comparison in EQ4 is
230 cases against 25, which is why W03 records that suite A is *not* thin and
why D-013 re-scoped EQ4.

## 6. `harness/` — what each module does

### `runner/scenario.py` — loads and validates a scenario

Reads one YAML file and checks it carries the required fields, that the
category and severity come from the fixed vocabularies, and that every step
names a helper that exists. Structural checks only: whether a scenario is
*good* was T11's judgment and belongs to a person.

### `runner/steps.py` — the 16 things a scenario can do

`reset`, `goto`, `back`, `reload`, `register`, `sign_in`, `sign_out`, `fill`,
`select`, `click`, `open_task`, `post`, `request`, `compare_responses`,
`capture`, `note`. **Not one of them asserts.** Each performs an action and
records what it saw. A scenario is data: adding one means writing YAML, not
Python.

### `runner/runner.py` — executes a scenario against a running version

Drives a browser through the steps, captures what changed after each one, and
hands the result to the collector. A step that cannot be carried out is
recorded and the run continues — a scenario that could not be executed is
evidence about the version, not a broken experiment.

### `evidence.py` — writes the bundle

One directory per run, named with a random token. Writes `trace.json` (what
the judge receives), `trace.md` (the same content for a person), `console.log`
and `network.jsonl`. **Scrubs version words and absolute paths** from
everything before writing, and appends the run-id → version row to
`data/run_manifest.jsonl` — the only place that mapping lives.

### `judge.py` — asks the model

Covered in §7.

### `compare.py` — puts two sets of verdicts side by side

Joins verdict files on `run_id`, compares only the runs both sources judged,
and prints the version column **only** with `--reveal`, read from the
manifest. Refuses to print an agreement statistic on a small sample, because a
percentage over three runs invites being quoted.

## 7. What `harness/judge.py` actually does

```
python -m harness.judge --bundle evidence/<run_id>
```

1. **Reads the bundle.** Opens `trace.json` and splits it into the scenario
   (preconditions, user action, expected behaviour, expected evidence,
   requirements) and everything else (the steps, the final state).
2. **Builds the prompt.** Loads `logs/prompts/P-003.txt`, which has two slots,
   `{SCENARIO}` and `{TRACE}`, and substitutes them. About 4,700 bytes. The
   prompt is frozen at M5 and this module never edits it.
3. **Finds the key.** `GEMINI_API_KEY` from the environment, or from `.env` —
   read UTF-16-tolerantly, because PowerShell redirection writes UTF-16. The
   key never reaches a file, a log or a verdict record.
4. **Calls the model.** One POST, temperature 0, JSON response requested.
   Retries 429 (quota) and 503 (overloaded) with exponential backoff, up to
   five attempts, per D-011. **Halts the run if a different `modelVersion` is
   served** than the one asked for — a run judged by two model versions is not
   one measurement.
5. **Parses the reply.** Strips a markdown fence if present, finds the JSON
   object even with prose around it, and rejects a verdict outside
   `satisfied` / `not_satisfied` / `uncertain`, or an empty evidence list.
6. **Records.** Prints the verdict, and with `--out` appends one JSON line per
   run. **A run with no usable verdict is recorded as having none — never as
   satisfied** (D-015). Reading the judge's own failures as evidence that the
   software works would bias exactly what EQ3 measures.

`--dry-run` prints the prompt and makes no call, which is how to inspect what
the judge will see without spending a request.

What it does **not** do: see the version, see any other run, see what the
other judge said, or decide anything beyond the one scenario in front of it.

## 8. The tags, and what each one freezes

| Tag | Freezes | Fixed before |
|---|---|---|
| `prereg-w01` | the decision thresholds | any data existed |
| `req-v1.1` | the 30 requirements | V0 was generated |
| `v0` | the clean application | defects were designed |
| `scenarios-v1` | the 47 scenarios | V1–V3 were built |
| `v1` `v2` `v3` | the three defective versions | anything was judged |

That ordering is the project's defence against "you tuned this after seeing the
results". The tags are dated, so a reader can check rather than take your word.

## 9. What you actually run

```
# validate the library, no browser needed
python -m harness.runner.runner --check

# execute scenarios against whichever version is checked out
npm --prefix app run reset
cd app && node server.js            # second terminal
python -m harness.runner.runner --scenario ACC-01 --version V0
python -m harness.runner.runner --all --version V0

# judge (note: the defect branches do not carry judge.py)
git checkout feature/week01-v1
python -m harness.judge --bundle evidence/<run_id> --out data/verdicts.jsonl

# compare
python -m harness.compare --judge data/verdicts.jsonl --human data/human-verdicts.jsonl
python -m harness.compare --judge ... --human ... --reveal
```

`--version` is not cosmetic: it is what gets written to the manifest, and it is
how a run is traced back to a version after judging.

## 10. Where to look for why

- **`logs/decision-log.md`** — every choice that could change a result, dated,
  with an index table at the top. Append-only: a reversal is a new entry, not
  an edit.
- **`logs/prompt-log.md`** — every prompt sent to a model, with the model, the
  version, and what came back. P-002 records a prompt that was *lost*, because
  a gap belongs in the record too.
- **`records/W0*/`** — what each week delivered, with an AI-use table.
- **`defects/README.md`** — the rules defect selection had to follow, written
  before any defect was chosen.
